1

QUESTION

FMOD도 코드로 제어하는데, 왜 직접 스크립트가 NGO 동기화에 유리한가?

어차피 FMOD 미들웨어를 사용하더라도 코드로 재생과 정지를 제어하는데, “NGO를 사용 중이므로 네트워크 객체에서 사운드를 재생할 때 가벼운 스크립트로 제어하는 것이 동기화(RPC) 및 관리에 훨씬 유리하다”는 것은 무슨 의미인가?

결론: FMOD라고 해서 NGO 동기화가 본질적으로 불리해지는 것은 아닙니다. 문서의 “훨씬 유리하다”는 표현은 과도하게 단정적입니다.

NGO가 실제로 동기화하는 것

일반적으로 NGO는 오디오 샘플 자체를 전송하지 않습니다. 서버는 “어떤 사건이 발생했다”거나 “어떤 사운드를 재생하라”는 명령과 상태를 전달하고, 각 클라이언트가 로컬 오디오 시스템으로 재생합니다.

게임 이벤트 보스 공격 또는
플레이어 스킬 발생
→
NGO 메시지 RPC 또는 상태로
사운드 ID·시각 전달
→
로컬 재생 AudioSource 또는
FMOD EventInstance 사용

로컬 재생 코드만 다를 뿐, 네트워크 흐름은 본질적으로 같습니다.

// Unity 기본 오디오
audioSource.Play();

// FMOD
RuntimeManager.PlayOneShot(fmodEvent, position);

“가벼운 스크립트가 유리하다”의 현실적인 의미

사운드 종류와 동작이 단순하다면 자체 SoundManager의 API를 프로젝트의 RPC 구조에 정확히 맞출 수 있으므로 관리 계층이 줄어들 수 있다는 뜻으로 해석하는 것이 적절합니다. 이는 FMOD의 네트워크 성능이 나쁘기 때문이 아니라, 단순한 요구사항에서는 직접 만든 시스템의 구조가 더 작을 수 있기 때문입니다.

반대로 복잡한 사운드는 FMOD가 더 단순할 수도 있습니다. 서버가 이벤트 ID와 RPM, Phase 같은 파라미터만 보내고, 클라이언트가 하나의 이벤트 인스턴스에 반영하도록 구성할 수 있기 때문입니다.

RPC만으로는 정확한 오디오 동기화가 되지 않는다

RPC를 받은 즉시 재생하면 네트워크 지연과 프레임 차이 때문에 클라이언트마다 시작 시점이 조금씩 달라질 수 있습니다. 정확한 동기화가 필요하다면 FMOD와 Unity 기본 오디오 모두 별도 설계가 필요합니다.

  • 서버 기준 시작 시각 전송
  • 늦게 받은 클라이언트의 재생 위치 보정
  • DSP clock 기반 예약 재생
  • 루프 사운드의 현재 상태와 타임라인 복원
  • 중복 또는 지연 RPC 처리
정리: 자체 스크립트는 단순한 프로젝트에서 NGO와 결합하기 편할 수 있지만, FMOD도 동일한 방식으로 RPC와 결합할 수 있으며 네트워크 동기화 측면에서 본질적으로 불리하지 않습니다.
2

QUESTION

FMOD의 parameter seek와 최대 인스턴스 제어를 Unity에서는 직접 만들어야 하는가?

FMOD의 파라미터 seek 기능이나 동일한 EventDescription으로부터 만들어지는 최대 EventInstance 수를 제어하는 기능은 AudioSource나 AudioMixer를 사용할 경우 직접 코드로 만들어야 하는가?

결론: 대체로 맞습니다. 단순한 대체 기능은 쉽게 만들 수 있지만, FMOD와 동등한 범용 정책과 도구까지 구현하려면 작업 범위가 커집니다.

Parameter seek speed

FMOD의 parameter seek speed는 파라미터가 새 목표값으로 즉시 점프하지 않고 지정된 속도로 접근하게 합니다. Unity의 AudioSource나 AudioMixer.SetFloat()에는 같은 형태의 범용 파라미터 seek 시스템이 없으므로 보간 로직을 직접 작성해야 합니다. 

currentValue = Mathf.MoveTowards(
    currentValue,
    targetValue,
    seekSpeed * Time.deltaTime
);

audioMixer.SetFloat("EngineVolume", currentValue);

AudioMixerSnapshot.TransitionTo()로 일부 전환을 처리할 수는 있지만, 게임의 연속적인 파라미터를 다양한 오디오 속성에 매핑하는 FMOD 시스템과 완전히 같지는 않습니다.

이벤트별 최대 인스턴스와 voice stealing

FMOD에서는 이벤트별 최대 동시 인스턴스 수를 지정하고, 한도를 넘을 때 기존 인스턴스를 어떻게 처리할지 정책을 둘 수 있습니다. Unity 기본 오디오로 같은 동작을 만들려면 사운드별 재생 목록과 제거 정책을 직접 관리해야 합니다.

기능 FMOD Unity 기본 오디오
파라미터 목표값 보간 Parameter seek speed로 설정 MoveTowards, SmoothDamp 등으로 직접 구현
이벤트별 최대 재생 수 이벤트 단위 정책 설정 사운드 ID별 AudioSource 목록과 카운터 구현
한도 초과 시 처리 Stealing 정책 사용 오래된·조용한·먼 인스턴스 등을 직접 평가
전체 voice 우선순위 미들웨어의 voice 관리 활용 AudioSource.priority와 플랫폼 voice 설정 활용 가능
정리: 간단한 최대 동시 재생 제한은 AudioSource 풀과 카운터로 충분할 수 있습니다. 하지만 거리·볼륨·우선순위를 고려하는 voice stealing과 파라미터 매핑까지 구현하면 자체 시스템도 빠르게 복잡해집니다.
3

QUESTION

Bank와 샘플을 언로드할 수 있는데 FMOD 오버헤드는 왜 남는가?

FMOD는 Bank 및 샘플 데이터를 로드·언로드할 수 있는데도 “엔진 위에 또 다른 엔진을 올리는 구조라 빌드 용량과 런타임 메모리 오버헤드가 필연적으로 발생한다”는 것은 무슨 의미인가? 라이브러리 자체가 포함되기 때문인가? 필요한 기능만 직접 만들면 사용하지 않는 코드가 없어 메모리 효율이 더 좋아진다는 뜻인가?

결론: Bank 언로드로 관리하는 콘텐츠 메모리와, FMOD 런타임을 탑재함으로써 생기는 고정 비용은 서로 다른 항목입니다.

Bank 언로드로 줄일 수 있는 가변 비용

  • 압축된 오디오 또는 디코딩된 샘플 데이터
  • 해당 Bank에 들어 있는 이벤트 메타데이터
  • 로드된 사운드 리소스와 관련 콘텐츠

오디오 샘플은 전체 메모리에서 큰 비중을 차지할 수 있으므로 Bank를 적절하게 나누고 언로드하는 것은 실제로 매우 효과적인 최적화입니다.

Bank를 내려도 남는 고정 비용

  • FMOD Core 및 Studio 네이티브 라이브러리
  • DSP, 믹싱 시스템과 오디오 버퍼
  • 채널·보이스 관리 자료구조
  • Studio 이벤트 시스템과 명령 큐
  • 오디오 처리 스레드
  • Unity–FMOD 연동 코드, 핸들, 콜백과 인스턴스 추적 데이터

따라서 Bank 언로드는 주로 콘텐츠 메모리를 회수하지만 FMOD 시스템을 초기화한 뒤 유지되는 런타임 자체의 비용까지 없애지는 않습니다. 플랫폼별 네이티브 바이너리가 빌드에 포함되기 때문에 빌드 용량도 증가합니다.

“엔진 위에 또 다른 엔진”이라는 표현의 한계

Unity 기본 오디오에도 이미 오디오 스레드, 믹서, DSP, 버퍼, voice 관리, 압축 해제와 공간 음향 처리 비용이 존재합니다. FMOD를 사용한다고 이 비용이 단순히 정확히 두 배가 되는 것은 아닙니다. 실제 비용은 플랫폼, 동시 재생 수, Bank 구성, 코덱, 스트리밍 설정과 Unity 기본 오디오의 병용 여부에 따라 달라집니다.

비용 구분 대표 항목 Bank 언로드 효과
콘텐츠 비용 샘플, 스트리밍 데이터, Bank 이벤트 메타데이터 직접적으로 감소
런타임 고정 비용 라이브러리, 스레드, 버퍼, 믹서, 내부 자료구조 대부분 유지
빌드 용량 플랫폼별 FMOD 바이너리와 통합 코드 변화 없음
프로젝트 구현 비용 파라미터, 풀링, stealing, 디버깅 도구 FMOD가 제공하거나 자체 구현

필요한 기능만 직접 만들면 항상 더 효율적인가?

요구사항이 작다면 FMOD 네이티브 런타임과 Studio 계층을 포함하지 않으므로 빌드 크기와 고정 메모리를 줄일 가능성이 있습니다. 다만 “사용하지 않는 코드가 없어서” 런타임 메모리가 크게 절약된다는 설명은 핵심이 아닙니다. 실행되지 않는 관리 코드가 반드시 큰 메모리를 차지하는 것은 아니며 일부는 빌드 스트리핑 대상이 될 수 있습니다.

반대로 FMOD 기능을 직접 재현하기 시작하면 AudioSource 풀, 이벤트 레지스트리, 파라미터 시스템, voice stealing, 페이드, 우선순위와 디버깅 도구가 다시 생깁니다. 요구사항이 커질수록 “가벼운 자체 시스템”도 작은 미들웨어처럼 커질 수 있습니다.

정리: FMOD에는 Bank 관리로 제거되지 않는 바이너리·런타임 계층의 고정 비용이 있습니다. 그러나 그 비용이 실제 프로젝트에서 중요한지는 대상 플랫폼의 빌드와 프로파일링 결과로 판단해야 합니다.

Final perspective

프로젝트 선택 기준

NGO 사용 여부만으로 FMOD를 배제할 근거는 부족합니다. 사운드 시스템의 실제 복잡도와 팀의 작업 방식, 그리고 대상 플랫폼에서 측정한 비용으로 결정하는 것이 합리적입니다.

Unity 기본 오디오가 적합한 경우

사운드 동작이 단순하고 볼륨·피치·풀링·간단한 페이드 정도만 필요하며, 프로그래머 중심으로 시스템을 관리하는 경우.

FMOD가 적합한 경우

파라미터 기반 변화, 복잡한 레이어링, 이벤트별 polyphony, timeline, transition, 프로파일링과 디자이너 중심 반복 작업이 필요한 경우.
